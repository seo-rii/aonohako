# CPU feature policy

`POST /compile` and `POST /execute` accept `disallowed_cpu_features`.
Compilation can reject selected instruction families in C/C++ objects;
execution can check and stop instructions reached by a native Linux
x86-64 contestant binary. These are separate opt-ins: the judge supplies the
field on each request that needs it. Omitting the field, using an empty array,
or using `null` preserves the existing behavior.

```json
{
  "lang": "CPP17",
  "sources": [
    {"name": "Main.cpp", "data_b64": "aW50IG1haW4oKSB7IHJldHVybiAwOyB9Cg=="}
  ],
  "disallowed_cpu_features": ["avx"]
}
```

The example compiles `int main() { return 0; }` with the AVX restriction.
Language aliases and `version` retain their existing meanings.

| Value | Restriction |
| --- | --- |
| `avx` | Reject AVX-family instructions, including AVX2, AVX-512, and mask-register operations. Baseline SSE/SSE2 remain available. |
| `simd` | Include the AVX restriction and reject packed SIMD arithmetic/logic and MMX operations. During compilation, also disable automatic loop and SLP vectorization. |

`simd` permits scalar SSE floating-point instructions, ordinary register/data
moves, and same-register zeroing idioms used by the compiler and the x86-64
calling convention. It is a restriction on vector computation rather than a
ban on every use of an XMM register. Specifying both values is valid but
redundant. The list accepts at most two values. Values are lowercase and exact;
unknown values and duplicates are invalid. Compilation accepts the policy for
C/C++ only. Execution accepts runtimes normalized to `binary`, including native
language aliases, and verifies the actual executable before launch. Unsupported
languages are rejected instead of silently ignoring the policy. A frontend
can forward the policy to an appropriate remote worker.

## Compilation and diagnostics

Each C/C++ translation unit is compiled to an object with the selected
compiler restrictions and link-time optimization disabled. The worker runs
`objdump` inside the compile sandbox, checks the disassembled code, and then
links those same inspected objects. Every submitted translation unit is
checked, including code originating from included headers or generated by
templates. Trusted library code added by the linker is outside this inspection.

This extra inspection matters because GCC permits a function's `target`
attribute or a `#pragma GCC target` directive to select a different instruction
set from the command-line default. Emitted instructions remain subject to the
object check even when enabled this way. See the
[GCC attribute documentation](https://gcc.gnu.org/onlinedocs/gcc/Common-Attributes.html)
and [GNU objdump documentation](https://sourceware.org/binutils/docs/binutils/objdump.html).

A detected instruction produces a `Compile Error`, no artifacts, and
`reason_code: "disallowed_cpu_feature"`. Its human-readable `reason` identifies
the source file and instruction. Unknown or duplicate policy values produce
HTTP 400 with `invalid_disallowed_cpu_features` before compilation or source
URL fetching. Oversized lists use the API's `invalid_request` collection-limit
error. Direct compiler calls return `Invalid Request` for invalid policies
or unsupported worker architectures.

Incomplete inspection also prevents artifact publication. Undecodable output,
inspection warnings, or disassembly exceeding the 1 MiB capture cap for one
object produce `cpu_feature_inspection_failed`. Inspector failures retain
their failure status; an inspection timeout remains a timeout. Successful
inspection output is not included in compiler diagnostics.

## Compile scope

This is a conservative static compilation policy. A scalar expression that
the compiler lowers to a packed bitwise instruction, such as some floating
point sign or absolute-value operations, can be rejected by `simd`. Inline
standard-library implementations are checked when they become part of the
submission object. Conversely, source code optimized away before object
generation has no instructions to reject. Policy behavior is therefore tied
to the compiler version as well as the source.

Static disassembly alone does not cover code reached through embedded data,
jumps into instruction bytes, or runtime code generation. Linked
libc/libstdc++ code is outside the compile check. Supply the execution policy
as well when the problem requires checking the instructions actually reached.

## Execution and diagnostics

Pass the compiled artifact back with the same policy:

```json
{
  "lang": "binary",
  "binaries": [
    {"name": "Main", "data_b64": "<artifact data_b64>", "mode": "exec"}
  ],
  "stdin": "",
  "expected_stdout": "",
  "limits": {"time_ms": 2000, "memory_mb": 256},
  "disallowed_cpu_features": ["avx"]
}
```

The worker requires an ELF64 x86-64 executable with a loadable entry point.
Both static and dynamic ELF executables are accepted. Scripts, other
architectures and unsupported runtimes do not fall back to unrestricted
execution.

The worker runs the contestant through Durante's pinned DynamoRIO runtime.
Durante inserts a check immediately before each decoded forbidden application
instruction. This covers raw instruction bytes, code reached at a new
instruction boundary, generated or modified code, and followed process/thread
lifetimes. Translating an unreachable instruction does not itself cause a
violation. Binaries compiled elsewhere receive the same runtime policy.

The execution policy applies to the whole application, including dynamically
or statically linked libraries. An otherwise scalar program can pass the
compile check and receive `Runtime Error` under `simd` when a library routine
executes packed SIMD. Scalar SSE floating-point operations, permitted register
moves, and zeroing idioms remain available. DynamoRIO and Durante's own
instrumentation are outside the application instruction stream.

Native filesystem, process and thread behavior remains subject to the existing
sandbox. The API rejects these unsupported combinations before downloading
binary URLs or admitting work:

- `communication` mode and contestant `enable_network`;
- contestant `file_outputs` or `sidecar_outputs`;
- legacy step file handoffs and Pipeline V1 `participant_file` outputs;
- contestant runtime languages that do not normalize to `binary`.

Ordinary execution, an interactive contestant, legacy steps using stdout
handoffs, and Pipeline V1 batch/interactive contestants are supported. Every
contestant step inherits the policy. Trusted interactors and SPJs do not
inherit it; Pipeline V1 can still use its interactor's output file as a private
artifact. A program used as an interactor in one step and a contestant in
another is restricted for the contestant invocation.

Invalid values and unsupported request combinations return HTTP 400
`invalid_request`. A missing or unusable enforcement backend, or an unsupported
executable, returns `Container Initialization Failed`. An execution policy
violation returns `Runtime Error` with `verdict_source: "cpu_feature_policy"`.
Step failures add their usual `step:<id>:` prefix to the top-level source.
Pipeline V1 retains its normal diagnostic redaction, so its public reason can
be generic while the verdict source remains available.

The policy can be combined with `work_measurement` and its existing diagnostic
limits. Both use one Durante execution and the native
`bb_entry_app_instructions` metric, with unchanged REP accounting. Measurement
still requires its normal operator opt-in and runtime configuration. A
policy-only request uses the packaged runtime without that measurement opt-in
and does not add a work-measurement field to the response. A policy violation
has no partial work totals. Exit code 126 alone is not a violation; the worker
requires a matching policy record. An ordinary crash after a verified policy
startup remains a normal runtime error. Existing time, memory and work-limit
verdicts retain priority.

CPU time, wall time and memory usage include native instrumentation overhead.
The existing helper, seccomp, bounded address-space reservations, resource
limits and configured cgroups continue to apply.

This uses Durante's existing `application_mutable` trust model. Application
code and the instrumentation share an address space, so a hostile application
may tamper with instrumentation or reporting. The policy is not an authenticated
security boundary. Work measurements remain diagnostic, with
`integrity_verified: false` and `trusted_verdict_eligible: false`.

## Operator packaging

The repository's [Dockerfile](../Dockerfile) and
[runtime Dockerfile](../docker/runtime.Dockerfile) build and package Durante
from the checked-in [source manifest](../third_party/durante/UPSTREAM.json).
The SDK and corrected runtime source are hash-pinned. The runner expects the
protected installation at:

```text
/opt/durante/dynamorio/bin64/drrun
/opt/durante/lib/libdurante.so
```

For a custom image, verify the vendored source, prepare the pinned SDK, build
the client and use [`install_durante_runtime.sh`](../scripts/install_durante_runtime.sh)
to copy the required libraries, runtime manifest and licenses. Keep the whole
installation operator-owned and unwritable by sandbox users. The worker
verifies the prepared release core and requires matching native policy
metadata, so an old client cannot silently ignore an enabled policy. The
existing `AONOHAKO_DURANTE_DRRUN` and `AONOHAKO_DURANTE_CLIENT` settings can select
another installation of the same reviewed runtime.

Build against the final runtime's base image; the legacy Python image uses its
own builder. SDK preparation supports Python 3.10 or newer. The Durante
integration workflow exercises the real root sandbox, policy-only execution,
combined measurement, guest faults and resource limits. With a prepared native
installation and root privileges, the policy suite can also be run directly:

```sh
AONOHAKO_ENFORCE_SANDBOX_TESTS=1 go test ./internal/execute \
  -run '^TestRunCPUFeaturePolicyInRootSandbox$' -count=1
```

## Judge integration

The judge must supply its chosen policy separately when compiling and executing
contestant code, and include it in compilation and execution cache keys.
`problem_id` does not select a CPU feature policy automatically. Compile
special judges and interactors with their own chosen policy. Execution does
not trust prior compile metadata: it verifies the selected executable and
applies the requested runtime policy independently.

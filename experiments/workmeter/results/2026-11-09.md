# Cloud Run interpreter work-meter validation — 2026-11-09

CPython IR counts were much more repeatable than CPU time for the selected
submissions. The expanded corpus also exposed work that these counters do not
measure. PyPy JIT counters had larger coverage gaps. This validates a research
tool, not a replacement for production CPU milliseconds or TLE enforcement.

[Machine-readable aggregates](2026-11-09.json) retain the full statistics,
boundaries and provenance hashes. Student sources, inputs and raw private
execution reports are excluded from this repository.

## Design and completion

- Source: `6b161cd76ccbe11301eecf98353f2a98fa70f51b`, based on main
  `30d5cd837fae1d60b366ce111f7c1d0dcf8a1147`; model `llvm-ir-v1`.
- Four Cloud Run gen2 instances in `asia-northeast3`, each 1 vCPU, 4 GiB,
  request concurrency 1, startup CPU boost disabled. Observed CPU models were
  AMD EPYC 7B13, Intel Xeon 2.20 GHz (two instances), and Xeon Platinum 8481C.
  Distinct instance identities do not prove distinct physical hosts.
- CPython 3.13.5: matched plain and instrumented source builds, both with hash
  seed 1 and the `-I -S` runner prefix. The control is not the live production
  interpreter. This cohort does not compare fixed versus random hash seeds.
- PyPy 7.3.19 / Python 3.11.11: direct execution versus mapped JIT counters;
  default hash policy retained.
- 58 public workloads plus five selected original cases: three serial repeats
  per instance, and three two-process repeats for the five original cases and
  14 largest public workloads. Orders were randomized in advance; failed
  observations were retained without selective retries.
- **2,424 main executions** (1,512 serial, 912 interference stress) plus
  **72 executions** in a separate four-service fanout test. All expected batches,
  outputs, exit conditions and raw-report contracts passed. Offline analysis
  recomputed the reports against 271 native metadata files: exit 0.
- The public-only README preparation flow was separately built under umask 077:
  116 serial executions and four stress executions passed, including PyPy file
  access as UID 65532. These preflight executions are not in the Cloud Run CVs.

CPU is final `wait4` user + system time for the diagnostic target process,
including launcher, interpreter initialization, target, report serialization
and teardown. Work units are weighted instrumented operations; they are not
milliseconds. CV below is population standard deviation divided by mean.
The statistics describe this one-date cohort; four instances and three serial
repeats each do not establish deployment-wide confidence intervals.

in the instrumented arm. The scales change fixed work, not a timed loop.

| Runtime / family | CPU ratio | Work ratio | Observation |
|---|---:|---:|---|
| CPython / hashlib | 3.202× | 1.000315× | External hashing work omitted |
| CPython / zlib | 3.150× | 1.000162× | External compression work omitted |
| PyPy / hashlib | 2.591× | 1.000000× | Native work omitted |
| PyPy / zlib | 3.091× | 1.000000× | Native work omitted |
| PyPy / large integers | 3.932× | 1.000000× | Cost outside mapped JIT segments |
| PyPy / strings | 2.759× | unavailable | No positive mapped work at any scale |

CPython pure Python, sorting, strings and regex scores grew about 3.65–3.83×;
large-integer work grew 11.16× versus CPU 8.17×. These workloads involve different
algorithms and startup contributions; their ratios do not establish one universal
work-to-time conversion. Passing internal counter integrity checks cannot detect
work outside the instrumentation boundary.

## Exit and resource-limit behavior

All eight boundary conditions per runtime had the expected process outcome
in 12 serial observations per arm. CPython normal return, SystemExit and Python
exceptions retained a partial report. Immediate `os._exit`, CPU-limit termination
and wall-limit termination produced no completed report. Both CPython builds
reject new threads and mark the measurement invalid.

PyPy CPU/wall/immediate termination also produced no report. Its short normal,
SystemExit(0) and thread examples had no positive mapped work; exception and
nonzero SystemExit reports were invalid. These expected unavailable/invalid
states are preserved, not converted into zero execution cost or successful
measurement. The thread boundary checks policy behavior, not multithreaded
accounting correctness.

## Decision and remaining work

Keep this implementation under `experiments/`. It supplies reproducible evidence
that counting covered work can remove most timing noise, and concrete tests
showing why these particular counters cannot replace production timing yet.

Production adoption needs a trustworthy accounting boundary outside student
control, coverage of external native operations and variable-sized intrinsics,
a defined policy for forced termination, and a separately validated mapping to
existing limits. PyPy also needs accounting for interpreted execution, JIT
compilation, GC and unmapped native work. Treating a missing portion as CPU time
and adding it to work units would require a new model and validation.

All three remote builds completed successfully. The experiment's four services
and revisions, two image packages (including the public-review tag), and owned
GCS staging objects were removed; three absence checks passed. Collection,
analysis, public reproduction and cleanup all finished with exit 0. Production
services and time-limit policy were not changed.
